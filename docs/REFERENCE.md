# Interaction and appearance reference

The implementation was compared with these primary sources and their visual demonstrations:

- [Google's launch announcement and original demonstrations](https://blog.google/products-and-platforms/products/search/google-circle-to-search-android/). The embedded **S24 Thrift Flip** video shows a short stroke over words becoming a blue text selection, a floating Copy/Translate pill, and a white results sheet. The **OOTD Pixel 8 Pro** video shows the white circle/scribble stroke, image corner brackets, and sheet expansion and dismissal.
- [Google's Circle to Search help](https://support.google.com/android/answer/14508957?hl=en) describes the gesture types, adjustable selections, search refinement, and results sheet.
- [Android's Circle to Search page](https://www.android.com/ai/circle-to-search/) includes a newer bag-selection demonstration. It preserves the white gesture, neutral sheet, white image corners and bottom search field.

Visual reference frames were inspected at roughly 2-second intervals, including the active stroke, resolved text selection, first results, expanded sheet, and return to the original screen. Reference media were downloaded only into `/tmp/cts-references`; they are not distributed with this project.

## Desktop adaptation

- Pure black translucent scrim; white gesture stroke; blue text highlights and handles. No purple palette or gradient stroke.
- Top close button, centered Google label, overflow menu, bottom search pill.
- Gestures resolve locally against OCR character boxes. Latin text snaps to words; Japanese remains selectable by character without inserting artificial spaces.
- A perfect horizontal line is valid. Its coordinates must survive even though its bounding rectangle has zero height.
- Search begins after selection by default. `--no-auto-search` keeps selection and copying local until Enter is pressed.
- Google's real web results render inside an expandable native sheet using Qt WebEngine. Result destinations and new-tab links go through the system's default URL handler and dismiss all CtS overlays. Search tabs, image previews, Translate and verification retain embedded navigation. The browser rejects a departing navigation before queuing the handoff, avoiding a reentrant WebEngine stop. The system request retains the click's Wayland activation context while CtS completes its exit transition.
- Image corner handles resize the crop; dragging inside it moves it. Text handles adjust the recognized range. Escape returns to selection before closing.
- Search fields remain editable and support adding words to an image search. The search pill can move to the top to expose obscured content.
- Dragging the Google logo or unused pill background moves the floating bar freely in both dimensions. In results, both that grip and the top handle apply horizontal movement and vertical resizing together, without a direction lock. Each pointer update changes the sheet's position and size together; resizing begins from its current rendered height if an animation is interrupted. Query selection and action buttons retain their normal behavior. Offsets survive page changes and expansion, with controls kept on screen.
- Native controls stop mouse propagation to the selection canvas. The canvas also rejects presses within the visible sheet and its opening destination, covering frames before the browser is ready and transparent mouse routing during dismissal. Moving or closing the sheet makes the uncovered desktop selectable again.
- The Wayland surface uses [LayerShellQt's overlay layer](https://github.com/KDE/layer-shell-qt/blob/master/src/interfaces/window.h) and the `utility` scope. [KWin maps unknown scopes to Normal](https://github.com/KDE/kwin/blob/master/src/layershellv1window.cpp), so the previous custom `circle-to-search` scope still received opening/closing effects despite being a layer surface. Utility windows are excluded from the standard Scale, Fade and Popup effects. Native checks inspect the actual Wayland protocol and evaluate the installed KWin effect filters.
- The desktop snapshot remains stationary. App-owned eased transitions reveal the neutral scrim and controls, fade resolved selection highlights, slide/resize the results sheet and move the active tab underline. Closing waits for all monitor overlays to finish their fade before quitting. Effects are applied only to simple native controls; the accelerated web surface keeps its own rendering path.
- The Copy/Translate capsule is raised after the results sheet is presented, so the sheet and its accelerated browser cannot cover it. A native regression check reproduces this with a contrasting browser background and verifies theme-colored popup pixels, the 1px gray divider, button input and animated entry/exit. Its position animation can retarget, while repeated layout updates leave an existing entrance fade running.
- Its graphics surface is prepared before mapping. Qt's first accelerated browser widget otherwise replaces the original raster native window with an OpenGL one, dropping the layer role and exposing the panel. Native tests check the window geometry during actual browser rendering, not only before selection.
- Browser pages render underneath an opaque cover matching the selected theme until their content is ready. Tab links preserve language preferences and trigger the same loading-cover path; verification forms remain interactive.
- Searches use the public web route with `hl=en`. The former Chrome side-panel parameters produced access-denied/rate-limit responses in live comparisons; the simple public route loaded real results in the same saved profile. The upload and results use one browser profile. Image-only/multimodal search modes follow Chromium's [Lens overlay URL builder](https://chromium.googlesource.com/chromium/src/+/main/chrome/browser/ui/lens/lens_overlay_url_builder.cc).
- [Qt's color-scheme hint is not supported by every platform theme](https://doc.qt.io/qt-6/qstylehints.html#colorScheme-prop). On the tested Plasma session its KDE plugin ignored the light override, and `matchMedia('(prefers-color-scheme:dark)')` remained true. The app selects Qt’s GTK3 platform theme before QApplication is created; its [requestColorScheme implementation](https://github.com/qt/qtbase/blob/dev/src/plugins/platformthemes/gtk3/qgtk3theme.cpp) supports both overrides. Native offline tests verify light/dark media preferences, matching loading frames and live changes without image inversion. Automatic mode watches Plasma’s `kdeglobals` window background (hex or RGB), falling back to the selected `.colors` file. The native dark palette uses Google’s charcoal `#22242a`, `#303134` fields, `#e8eaed` text and `#8ab4f8` accents. Google Translate’s semantic appearance switch is synchronized to the browser media preference because Translate does not follow it automatically. Its native theme supplies input, menu and icon colors. Its Material surface/background tokens (including RGB variants) are mapped to CtS’s neutral palette at Translate’s native dark palette provider, including its separately styled Google header, so the page background is exactly `#22242a` and standard panels use `#303134`. The live Translate check compares exact colors with the sheet and verifies switching back to light. Verification documents receive only a scoped dark background/text rule; isolated challenge frames remain intact. Manual modes persist separately. This affects only this process.
- A native tab row remains consistent across Google's changing All/Images/Videos interfaces. Google Translate retains its functional inputs while Sign in and Google apps controls are hidden.
- AI Mode's answer lives before the ordinary `#rcnt` results node. Regular Search spacer cleanup must not hide those siblings in AI Mode; a separate path preserves the answer, citations and follow-up box. Both an offline semantic layout fixture and a live response check cover this regression.

This is a KDE implementation of the core interaction. Google's Android app, proprietary object segmentation, account integrations, audio search, live translation of scrolling apps, and phone-specific features are not available through its public web interface. An object tap creates a 200px adjustable crop; circling provides a more precise image region. The results themselves are Google's web interface and may differ from Android's.

## Japanese OCR

Models come from the official [tessdata_best repository](https://github.com/tesseract-ocr/tessdata_best) at the revision and SHA-256 digests recorded in `circle_to_search/tessdata/models.json`. Their Apache 2.0 license is included. English and Japanese load together by default. Vertical Japanese uses its dedicated model through the overflow menu or `--vertical`.

The OCR input is enlarged before recognition. hOCR character boxes are mapped back to screenshot coordinates and then to the monitor's logical coordinates. Tesseract can produce zero-width boxes for vertical characters; column ink projections recover their positions. Recognition is tested against generated horizontal, dark-background and vertical Japanese text, including small 12px kana/kanji. Recognition accuracy still depends on the source font, size and image quality.

Early gestures receive a separate local OCR crop with padding along the reading direction. Crop offsets are applied in physical pixels before converting to logical screen coordinates, including fractional display scaling. The original background scan stays available for later selections and extended handles. Generation tokens reject stale local results after a new gesture, clear action or language change. A late full result can expand an active selection's document only when the selected text matches; a timeout cannot erase a successful local selection.
